# Full-workflow acceptance harness

Updated: 2026-11-04

An opt-in engineering test that drives the real Ruloom command line through
the HyLogger product workflow and writes a machine-readable report. It
reports what the installed code actually did. It is not owner approval, not
the Test 1 comparison and not a product-readiness claim.

Files: [scripts/full_workflow_acceptance.py](../scripts/full_workflow_acceptance.py)
and [tests/test_full_workflow_acceptance.py](../tests/test_full_workflow_acceptance.py).

## What it does and does not do

It does:

- build the real wheel with the project's own `hatchling` backend, extract it
  into an isolated directory and run every step from there with the working
  directory outside the repository (the approach of `tests/test_wheel_cli.py`);
- run `prepare`, `run` (with the real human gate on piped input), the
  recipient-side verifier and offline replay through `engine.cli.main`;
- let the installed engine and profile make every validation, quality and
  acceptance decision.

It does not:

- call any model, paid service or network. Model responses are scripted mocks
  labelled `ENGINEERING-TEST-MOCK`, and the driver subprocess also disables
  sockets (an in-process guard, not an operating-system sandbox);
- mock validation, thresholds, quality decisions or the acceptance gate;
- use real source data. The source is an invented fixture generated by the
  harness. Its labels come from the installed vocabulary only so that the
  vocabulary checks apply; the assignment is a seeded pattern with no
  geological meaning. The fixture sidecar carries a licence field only to
  satisfy source-rights intake; it implies no real licence or origin;
- read credentials, tokens or environment values. The driver gets an
  allowlisted environment (names only are reported) and all captured text is
  redacted for bearer tokens, keys and secrets.

Automated gate input is an engineering test, never owner approval. The gate
note is fixed text beginning `ENGINEERING TEST AUTOMATED INPUT`. The engine
records `decided_by` as `human` for any piped input, so the label lives in the
note only; the harness records that as an observation.

## Running it

Nothing runs unless you opt in with `--run` or `RULOOM_FULL_WORKFLOW_ACCEPTANCE=1`.

```sh
.venv/bin/python scripts/full_workflow_acceptance.py --run \
  --report-dir runs/full-workflow-acceptance
```

Options:

- `--layout wheel` (default) builds and installs the wheel. `--layout tree`
  uses the source tree and is weaker because it gives no packaging evidence.
- `--python PATH` selects the interpreter for the driver and the wheel build
  (relative paths are taken from the repository root, for example
  `.venv/bin/python`). The interpreter must satisfy `requires-python` and have
  the project dependencies and `hatchling` installed.
- `--strict` makes this the final gate (see below).
- `--expect-head SHA` and `--expect-tree-digest DIGEST` pin the revision that
  was declared ready (see below).
- `--print-revision` prints the current commit and working-tree digest as JSON
  and exits. It reads git only, runs nothing and needs no opt-in, so the two
  values to pin can be read without starting a run. Exit 1 if git cannot say.
- `--report-dir DIR` writes each report to a new timestamped file and appends
  a line to `DIR/index.jsonl`. Files are created exclusively, so no earlier
  report is ever overwritten or deleted. Use a git-ignored directory such as
  `runs/`: a report directory inside the tracked tree changes the very tree
  digest the next run records.
- `--report PATH` writes one report and refuses to overwrite an existing
  file. Without either option the report prints to standard output.
- `--keep-work DIR` keeps the work directory for inspection.

Exit codes: 0 pass, 1 failure (any strict failure, or a product failure),
2 usage, 3 pending only, 4 not opted in, 5 inconclusive, 7 harness errors only.

Tests of the harness itself:

```sh
.venv/bin/python -m pytest tests/test_full_workflow_acceptance.py
RULOOM_FULL_WORKFLOW_ACCEPTANCE=1 .venv/bin/python -m pytest \
  tests/test_full_workflow_acceptance.py          # adds the live run
RULOOM_FULL_WORKFLOW_ACCEPTANCE=1 RULOOM_FULL_WORKFLOW_ACCEPTANCE_STRICT=1 \
  .venv/bin/python -m pytest tests/test_full_workflow_acceptance.py
```

The always-on tests check the harness logic, redaction, environment isolation,
the labelled fixture, the stability and strict logic, report preservation, and
the tamper helpers against the real consumer-side verifier. They also exercise
the real profile code with the role mock: the same-seed repair rules and the
research, assessment and review validators, including their refusals. The
live test checks the report is sound; the strict flag also requires the strict
gate to pass. One test runs `ruff check` and `ruff format --check` from the
existing `.venv` on the two Python files only. The repository's own
`Q-CODE-HYGIENE` gate runs the same two commands over the whole tree, so it can
fail on files this harness does not own even when these two pass.

## A stable revision, or no verdict

The wheel is built from the working tree, including uncommitted changes from
other workers. So the harness records the commit and a digest of the contents
of every changed or untracked file (`revision.tree_digest`) at the start, after
the wheel build and at the end. Ignored paths such as `runs/` and caches are
excluded.

If the commit or the tree digest differs between any two snapshots, or git
cannot report them, the run is `inconclusive`: the evidence mixes revisions.
The observed result is kept as `summary.observed_overall` for diagnosis and
`stability.paths_that_moved` names what changed, but no verdict is valid and
strict mode fails.

For the final run, pass the revision the owner declared ready:

```sh
.venv/bin/python scripts/full_workflow_acceptance.py --run --strict \
  --expect-head <commit> --expect-tree-digest <digest> \
  --report-dir runs/full-workflow-acceptance
```

A run that starts at a different revision is inconclusive before anything is
built. Read the two values to pin with `--print-revision`, or take the digest
from a report's `revision.tree_digest`.

## Status semantics and the strict gate

Every step ends as `pass`, `fail` or `pending`.

- `pass` needs a real assertion against real engine output.
- `fail` is an assertion that did not hold, or any unexpected error. Each
  failing step carries a `fault`: `product` (an assertion about engine or
  profile behaviour did not hold) or `harness` (a setup, driver or programming
  error in this harness, which says nothing about the product). A harness
  fault still blocks a pass. An unclassified failure counts as a product
  failure, so a failure is never hidden as a harness error.
- `pending` means the step cannot run because an interface or prerequisite is
  missing. It always names its dependency. Steps blocked by a failed root step
  are also pending and point at that root step, so one cause is not repeated
  as many failures. A step that needs a later stage first proves the run
  reached it; a run that died earlier never counts as a refusal.

A scenario takes the worst status of its steps, and an empty scenario is
pending. The overall result is `pass` only when every step passes. A report
that contains credential-shaped text cannot pass. `summary.verdict_kind` names
the meaning: `pass`, `product_failure`, `harness_error`, `incomplete`,
`inconclusive` or `report_hygiene_failure`.

`--strict` (or `RULOOM_FULL_WORKFLOW_ACCEPTANCE_STRICT=1`) is the final gate.
It passes only if all eight required scenarios exist and pass, with no failed,
skipped (scenario absent) or pending step, on a stable revision. The report's
`strict` section lists every reason it failed. Without `--strict` the same
section is still computed, but pending-only results exit 3 instead of 1.

### What the case controls prove

The harness never searches for a seed and never tunes a threshold: a plan that
fails the real case checks stays a failure. Three seeds are fixed in the script
and disclosed in the report under `fixtures.controls`:

- **Known-good release-positive control** (seed 9, 800 rows, balanced). The
  invented fixture with this plan passes every real case check and releases.
  Its provenance, stated plainly: it was first observed to pass in the
  exploratory runs preserved under `runs/full-workflow-acceptance-dev/` and is
  pinned here; the harness does not derive it. If it stops passing, the root
  step `case-accept-completes` fails and nothing replaces it. Every other case
  step needs this control to release first, otherwise it is pending, never
  pass.
- **Known quality-failure control** (seed 8, same plan). It fails
  `case.swir_answer_rate` (0.0279 observed against the 0.02 limit). With an
  "accept" supplied, the engine must still skip the gate and release nothing
  (`case-quality-failure-blocks-release`). If it ever stops failing, that step is
  pending, not pass.
- **Repair control** (seed 1, joint strategy). Its first attempt fails
  `case.inclusion_fraction`, so the repair stage runs. The reroll and correction
  steps check this precondition on the real run; if the first attempt does not
  fail, they are pending, not pass.

Swapping any of these for a seed that happens to pass would be a change to the
script in review, not something the run does.

The three product findings below stay open until the implementation workers fix
them and a strict run on the pinned revision shows the matching step passing.
The harness does not soften or skip those steps, and the report lists each
under `findings`, with its own step's real result (`open: reproduced`,
`not reproduced: candidate fix, confirm on the pinned revision`, or
`unverified`):

| Finding | Step |
|---|---|
| F1. Recipient verification expects `manifest.json` inside a ZIP that does not contain it. | `verify-case-anchor` |
| F2. Integrated repair reports success but leaves the joint strategy unchanged. | `case-supported-correction-same-seed` |
| F3. Unknown-case preparation calls the model before refusing. | `case-prepare-unknown-case-zero-calls` |

- **Manifest.** `generation.cases` must declare the case and its
  `catalogue_sha256` must equal the canonical digest of the installed
  `cases.json`. A copy of the installed packages with one catalogue number
  changed must be refused at `prepare` or at `run`, with nothing generated or
  released, and the refusal must cite the pin. The same route must first work
  untampered.
- **Seed.** The seed is never rerolled. The engine's own guard is tested by
  swapping a deliberately seed-rerolling repair capability into the real
  `execute()`: the run must be refused, cite the changed seed and release
  nothing. This shows the engine guard; it does not claim the shipped repair is
  the only way a seed could change.
- **Supported correction.** With the fixed repair control (seed 1, joint
  strategy) the run must show a failed first attempt, one `case_repair` event
  moving the plan to `fitted_markov_balanced`, a second attempt with the same
  seed, and no model consulted for the repair. The known-good control must
  release first. If the first attempt does not fail `case.inclusion_fraction`,
  the step is pending, never pass. The step reports the strategy of each
  attempt and whether the attempts produced identical artifacts, so a repair
  that reports ok but changes nothing is a failure, not a pass (finding F2). The
  corrected attempt must also stop failing `case.inclusion_fraction`, so a
  relabelled strategy with unchanged behaviour fails too. The control shows the
  correction works, not that the corrected run releases: in the preserved
  exploratory runs the corrected attempt cleared the inclusion failure and then
  failed a different check, so that run released nothing.
- **AI handoffs.** The role mock reads identity facts (case id, hashes, code
  verdict) from the real prompts so a valid handoff exists, then changes one
  field per negative control: an invented citation, a wrong source hash, and a
  reviewer verdict that contradicts the code. The reviewer's structured evidence
  facts quote exact values from the verified measurement paths the prompt
  lists, and the profile re-checks each one (an always-on test refuses a wrong
  value). A tampered handoff must not be
  recorded `ok` and its content must not reach any release member. The
  unmodified handoffs must pass first, and the tampered run must have reached
  the stage, or the step is pending.
- **Frozen evidence.** The decision's `frozen_manifest_sha256` must equal the
  canonical hash of the frozen member list, every frozen file must match its
  entry and the released bytes, and all case members must have been frozen
  before the decision. The evidence report must separate advisory AI output.
- **Recipient.** Every case recipient and case-tamper step depends on one root
  control, `verify-case-anchor`: the genuine accepted package must verify with
  the source unreachable. If it does not, a refused tampered package would
  prove nothing, so those steps are pending and only the root fails. With the
  source directory renamed away, `ruloom verify ZIP
  --require-case ID@VERSION` must verify and report the contract and catalogue
  digests. Correct `--expect-contract-sha256` and `--expect-catalogue-sha256`
  anchors verify; wrong anchors, a wrong case id and a wrong version are
  refused. `--source` accepts the true source and refuses another.
  The recipient who holds only the ZIP is tested separately. The verifier reads an adjacent `manifest.json` when available, can read one
  inside the ZIP, and otherwise resolves only trusted installed profiles by the
  case identity in the bundle. An explicit `--profile` must support that case;
  the accepted case release carries no manifest inside the ZIP. So the tamper and stripped-package refusals run
  on a ZIP alone in its own directory with `--profile hylogger --require-case
  ID@VERSION`, and `case-recipient-zip-only-verifies` first checks that a
  genuine ZIP verifies in exactly that situation with exactly those flags. If
  it does not, the refusals are pending, so a refusal can never be nothing more
  than "cannot pick a profile". A stripped lone ZIP must be refused with the
  anchor; without it the outcome is recorded under `observations`.

Other claims in the table:

- **Legacy repair.** The legacy route lets the repair model propose any seed,
  so `legacy-repair-bounded-and-visible` claims only that the failing attempt
  stays recorded and the attempt bound holds. Same-seed repair is proven by
  the case controls.
- **Rejection and acceptance.** Reject and unrecognised input must exit 2 with
  no `release.zip`, `release.sha256` or release `manifest.json`.
- **Tampering.** Edits use the engine's own packaging helpers so the checksums
  can be re-cut, as an attacker could. Each edit must be refused with the
  typed `ReleaseVerificationError`; any other error type counts as a failure.
  Without an external anchor a re-cut package is only as strong as its own
  checksums; that outcome is an observation, not a pass criterion.
- **Offline replay.** The saved `plan.json` is replayed with
  `--model-policy offline` and a model that raises on any call. Data, plan and
  seed must be byte-identical with zero model calls. For the case route the
  three AI stages must read `unavailable`, never `ok`, while every case check
  still runs.

The workflow follows the product route: `prepare` writes a draft and `run`
uses its `spec.json` with `--spec`. Under the default spec only the legacy
`fitted_markov_joint` strategy is accepted, so the balanced strategy reaches a
run only through a prepared spec.

## Dependencies the case steps rely on

The harness detects each interface from the installed layout and never
simulates one; a missing piece makes the dependent steps pending with the
exact dependency named:

- engine integration (parallel-engine-workflow-brief.md): `ruloom prepare
  --case ID@VERSION`, a `case` field in the spec, `generation.cases` in the
  profile manifest, and case checks bound into the runner and graph.
- engine integration: `ruloom verify` with `--require-case ID@VERSION` and the
  external anchors above, and the case members (`case-binding.json`,
  `case-contract.json`, `case-evidence.json`, `case-reference.json`,
  `case-utility.json`) packaged in `release.zip`.
- engine integration: runtime roles `case_research`, `case_source_assess` and
  `case_candidate_review` in the same graph, recorded as unavailable (never
  pass) under the offline policy.

The profile helpers in `profiles/hylogger/validation/workflow.py` are read for
`CASE_CHECK_IDS` and `CASE_MEMBER_NAMES`. A final strict run on one committed,
integrated revision is what turns these steps into settled pass or fail
results; runs on a moving tree are exploratory only.

## Report

The report is JSON with schema `ruloom.full-workflow-acceptance/1`:

- `revision`: commit, branch, working-tree state, `tree_digest` and the
  changed paths; `stability`: every snapshot, whether they matched, and what
  moved;
- `layout`, `environment` (interpreter versions and the environment policy,
  names only), `capabilities` (what the installed layout offers), and
  `fixtures` (labels, mock model label, gate note, case reference and the three fixed
  `controls` with their seeds), and `findings` (the three open product findings,
  each with its own step's real result);
- `scenarios`: each with `id`, `status` and `steps`; each step has `id`,
  `title`, `status`, `detail`, `dependency`, `evidence` and `fault`;
- `summary`: overall status, `observed_overall` when inconclusive, step counts,
  `product_failures`, `harness_errors` and `verdict_kind`; `strict`;
  `pending_dependencies`; `observations`; `model_calls_total` (mock calls
  only);
- `hashes`: wheel, fixtures, draft files, accepted data, plan, report, release
  ZIP, the decision-bound frozen digest, the case contract and catalogue,
  the replayed data and the harness script itself;
- `hygiene`: whether credential-shaped text was found; `limitations`.

## Limitations

- Mock responses and an invented source: nothing here measures a real model,
  real data, privacy, licensing or scientific validity.
- The network guard is in-process, not an operating-system sandbox.
- Tamper edits use packaging helpers from the repository tree while the
  verifier under test runs from the installed layout.
- The controller imports the shared hashing helper from the repository; it
  defines no hashing helper of its own.
- The role mock reads facts from the real prompts; a change to prompt wording
  shows up as a harness fault, not a product failure.
- The three control seeds are pinned and disclosed. The known-good seed was
  first observed to pass in exploratory runs, so it is a pinned observation and
  not an independently established fixture; if you hold an established
  known-good fixture and plan, replace the constants and the control stays
  labelled. The harness never searches for a seed or tunes a threshold.
- A wheel built from a shared working tree reflects whatever other workers
  changed at that moment, which is why a moving tree is inconclusive.
